# Owned author factory upgrade example

INI, JSON and Hjson share the existing `rw-reforge.factory.v1` author reader and cross-format `factory-base.ini` inheritance. T1 `spfactory` produces builder; terminal T2 `spfactoryt2` produces builder and c_tank. Both use the same existing LAND body/exit and footprints. T1 is 1200 HP, T2 is 1800 HP. The Hjson input includes Hjson comments.

The three optional upgrade fields must appear together: `upgradeTo=spfactoryt2`, integer `upgradePrice=2100` and positive finite binary32 `upgradeBuildSpeed=.004`. They create an ordinary upgrade action keyed by the resolved target ID, so the drawn action IDs are `upgrade:spfactoryt2` and `cancel-upgrade:spfactoryt2`. No factory/product/menu ID is added to an engine table. This finite first version accepts one terminal compatible factory target, with the same movement, foundation, collision/placement envelope and exit profile; references, self-targets, partial fields, malformed/nonfinite values and incompatible targets fail through the common content boundary. Existing native identity qualification remains strict.

Production and upgrading use one FIFO. Each explicit step advances only its current head; completing a job does not advance the next job in that same step. Cancellation refunds that paid upgrade without disturbing adjacent products. Death refunds pending products/upgrades once. On conversion the same unit ID, owner, position and heading remain. Author factories use the existing ordinary binary32 health ratio: 600/1200 becomes 900/1800. The exact qualified native sea factory keeps its distinct existing health setter behavior.

A target may remove a product: pending removed products refund once and their nonces stay retired. Units already produced remain valid against their actual birth definition; the host retains that birth provenance internally through the conversion. It adds no player DTO field. As with the existing lifecycle, a failed step publishes no partial charge, conversion or birth and can be retried at the same boundary.

The normal content menu selects a preplaced T1. With the ordinary 3000 budget, queueing the upgrade leaves 900; right-click cancellation restores 3000. After requeue/completion, builder500 plus c_tank350 leave50. Upgrade cards share the authorized factory action grid with products. Long lists scroll, clipped cards are not click targets, stale presses cannot survive selection/type changes, and unfinished author construction offers neither production nor upgrade actions. Full target, fee and nominal duration are in the tooltip; queue count/progress has its own line.

`extended/` changes only owned content: seven T1 products plus the upgrade use the same scroll region; the target unlocks an eighth product `sp_tank_8_after_upgrade`. Normal paid upgrade and the new product use the same common actions. The first target is deliberately terminal; this example does not promise arbitrary upgrade trees, new exit algorithms or new collision rules.

Formal Core fixtures use author factory inputs plus the existing strict native builder/tank sources. The tank's separate Core source keeps its native global replacement declaration; the normal enabled package omits that declaration with identical gameplay fields. The tooling labels `author-factory`, `author-producer` and `author-upgrading-producer` call the same real author reader and check the actual capability, so a wrong label cannot hide/invent queues. The three full1800-step contracts independently declare builder birth500, upgrade completion750, next builder1251 and newly enabled tank1752; payments leave6900 at0 and6550 at751. A separate300-step JSON case archives actual p1/p2 authorized views across conversion249.

All public pixels/maps come unchanged from the repository-owned `author-production` example, itself tracing to the existing owned construction/economy/tank fixtures. New T2 and alias files only inherit those definitions. No original-game source, extracted pixels or third-party code is distributed here. Private Windows validation borrows qualified original landfactory art for both new tiers and records its real provider/pixel origin separately; it does not imply unique artwork or original runtime compatibility.
