# Owned two-ship shore upgrade example

Use one of `ini`, `json` or `hjson` as the normal content root, enable its `package`, choose `spbuilder`, and leave sandbox placement off. All three formats inherit existing constructor, factory and named-weapon definitions. The package introduces `spdock`, `spdockt2`, `spcorvette` and `spfrigate` through content only; it adds no engine or menu ID registration.

The existing owned800x600 map has20-unit cells and a vertical water channel at x=[180,340). Select the own constructor at(110,210), approach(170,150), and build `spdock` at(250,150). Construction costs700, leaving2300 from the ordinary3000 budget. Unfinished construction offers no production or upgrade action. At completion, T1 offers `spcorvette` only.

Pay900 to upgrade the same factory into `spdockt2`; the full-health example becomes1800HP and leaves1400. The existing FIFO accepts `spcorvette` for350 and `spfrigate` for450, leaving600. These are two different authored IDs, with1200/1600HP,30-unit radius and0.8/1.0 movement speed. Both inherit port/starboard mounts and70/100 firing delays. A short70-unit range keeps their automatic guns out of reach of the original shore constructors while they emerge.

Select the first ship after birth, move toward(300,210) inside the water channel, then command the existing hostile constructor near(350,210). Both inherited guns can fire at the surface/land target. Select the second ship and sail toward(250,430). The current movement policy distinguishes normal command completion from subsequent braking and stable position; the coordinates are requests, not a new universal four- or seven-unit final-position tolerance. Validation records normal `movement-arrived`, actual stopping, lack of drift and legal water separately. No original-game numeric movement match is claimed.

A separate explicitly enabled sandbox case demonstrates underwater capability: `/spawn spfrigate 250 440 p1 heading=90`, then `/spawn navalUnderwaterTarget 300 480 p2`. These requests are queued for the next real step. Select the new ship and attack the existing fixed-8-height target. Only starboard has the underwater mask; port remains surface-only. Actual births, impacts and target health loss are checked. This free placement example is not the paid acquisition chain, and the fixed target is an existing diagnostic type, not a newly implemented submarine. The authored ships do not gain the native heavy-battleship-only sinking mechanism.

All public pixels and copied templates/maps come unchanged from the repository-owned author-shore/author-water and naval-production fixtures. Both ship IDs deliberately share the same owned sprites. `fixture-provenance.json` records each copied input and its SHA256. The authored costs, ranges and stats are demonstration choices, not original balance facts. Enable this standalone package by itself; other examples may declare the same constructor or fixed-target IDs.

The public acceptance declarations are `scenarios/author-naval-chain-{format}.json` with their Core contracts, and `platform/scenarios/author-naval-chain-{format}.json` with their normal Session contracts. Core captures3200 host steps; the ordinary Session captures3580 complete p1 player steps, including the explicit empty-to-four named-weapon arrays. These are distinct archive layers. The Core prelude starts the constructor at(110,150) for its fixed eastward approach; the normal menu and Session start at(110,210). Both use their existing fixture rules, without enabling new fog-of-war settings. The ordinary Session keeps its existing explicit null knowledge field. Runtime main sources are unchanged.
